# PR message for a codegen update

Prepare `Update to Tapir <version>` as the title unless the user supplies one or the final scope requires another. Save the body in untracked scratch storage and return a usable file link and title. If copyable Markdown in chat is requested, return the body in one fenced `markdown` block.

Establish the intended PR base from repository context. Base the message on the full proposed diff against that base, including relevant earlier branch commits and uncommitted/new deliverables. Keep unrelated work out of the proposal. Reconcile the report with the current diff; do not repeat stale counts or abandoned decisions. A changed dependency pin alone does not establish which commands became available.

## Contents

- Open with the previous/target Tapir versions, selected multiconn version and main capabilities added.
- For **40 or fewer newly exposed commands**, list all of them in a `Command | Description` table, grouped by domain only when helpful. Use underlying Tapir/Official command names and one-sentence descriptions. Include material Archicad version restrictions.
- For **more than 40**, give the total and summarize additions by capability/domain in a short list. Do not produce an exhaustive command table or split it into multiple tables to evade the limit. Restored commands count as newly exposed; replacing the implementation behind an existing public tool does not.
- Include a short list of commands newly excluded by this PR, with a brief reason. Qualify Tapir/Official names where needed. Mention restored exclusions when relevant; omit the unchanged baseline exclusion inventory. If there are many exclusions, group those sharing a reason rather than repeating explanations.
- Link to the repository-relative `scripts/codegen_reports/tapir-<version>.md` for review evidence.

Do not include changed-command lists, breaking-change or caller-migration sections. MCP agents retrieve current tool descriptions and schemas on each new run. Continue reviewing changed contracts internally to make correct generation/config decisions.

Pagination settings, image extraction and other routine generator implementation details belong in the internal report or diff. Keep them out of the PR message. Also omit test/verification sections, routine logs, local absolute paths, repeated feature inventories, empty headings and release-only autogenerated credits/changelog sections.

## Publication boundary

This skill prepares the PR message; it does not automatically commit, push, create a GitHub draft or open a PR. Follow the user's session authorization for any separate publication request. When opening a PR is authorized, use the reviewed proposed diff and message; with `gh`, pass the prepared body using `--body-file` to preserve Markdown and newlines.
